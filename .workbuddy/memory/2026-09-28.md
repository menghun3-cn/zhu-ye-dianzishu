## 2. 限速模型重测：旧结论**是错的**（本日最有价值的发现）

用户授权「你怎么设置都可以，目的全部下载完毕」，于是先把限速模型测准，再定参数。

### 新增两个探针（以后复测直接用）
- `tools/_diag_parallel.py` —— 同时握手 N 个包，串行 vs 并行对比聚合吞吐。
- `tools/_diag_sustain.py <fid_fast> <fid_slow> [快线MB] [慢线MB]` —— 两条线路同时拉、每 5s 采样，
  报告写 `%TEMP%\sustain.txt`（沙箱 stdout 可能看不到，要读文件）。

### 实测结果（决定性）
```
fast  165-usw-data.tv002.com   前 9.1s 拉了 9.04MB（971 KB/s）→ 之后恒定 16 KB/s
slow   94-cucc-data.tv002.com  前 85s 34 KB/s               → 之后也是恒定 16 KB/s
```

### 修正后的模型（三条）
1. **爆发额度 ≈ 9MB（不是旧的"30~100MB"），速率约 1MB/s。**
   旁证：09:40 那次会话启动后 139s 内下了 2.82+1.72+4.24 = **8.78MB** 就掉速；
   **静默 3.6 天之后重启，爆发也只有 8.8MB** → 额度有上限，静默再久也不会更大。
2. **地板 16KB/s 是"可以一直用的速率"，不是"被封"。** ← 最重要的认知修正。
   探针连续 600s 每 8s 稳定 128KB，一刻没停 → 额度耗尽后**继续下载就稳定拿 16KB/s**，
   不需要（也不应该）静默几十分钟等它。
3. **额度按账号/IP 共享，不按 CDN 主机。** 两条完全不同的线路（usw / cucc）在同一时刻一起掉到 16KB/s。
   → 「换主机」「多线程」都拿不到额外额度。之前看到 usw 跑 500KB/s 就以为它是好主机，**是错的**，
   那只是"额度刚好是满的"。

### 静默的盈亏平衡点 = 576 秒
静默 R 秒 → 得一笔爆发 9MB；一直下载 → 得 16KB/s × R。
R=576s 打平；R=900s 净亏 5.4MB；R=5400s 净亏 77MB。**静默超过约 10 分钟就是纯亏。**

### v3 参数（已生效，替代旧 v2 的 900/5400）
```
--workers 1 --limit 0 --loop
--rest-min 300 --rest-max 900 --probe-interval 300 --probe-kbps 40
--slow-window 8 --slow-bytes 65536          # 旧值 256KB(=32KB/s) 高于地板 16KB/s，会把正常下载误判成限速
--pack-timeout 10800 --max-rest-cycles 12 --max-attempts 3
```
- `slow-bytes` 必须**低于地板**（8KB/s），否则正常下载被判"限速"→ 触发无谓静默。
- `probe-kbps` 500→40：500KB/s 只在 9MB 爆发期内存在，要求 500 等于永不判"恢复"，一路静默到 rest-max。
- `pack-timeout` 1800→10800：地板速率下 100MB 的书要约 6400 活跃秒，旧值让**所有大书必然失败**。

### 可持续速率与工期（对用户要诚实）
| 口径 | 速率 | 248GB 需要 |
|---|---|---|
| 只吃地板 | 16KB/s | ≈173 天 |
| 地板 + 平衡点静默（理论最优） | ≈32KB/s | ≈86 天 |
| 09-24 实测（旧参数偏保守） | ≈29KB/s | ≈95 天 |

**三个月上下就是免费档的硬上限**，多线程/换主机都不改变这个量级。

## 4. 【修正】v4：把 503 当限速是最大的浪费；静默其实是纯亏（用户说「不开会员，一直下载就行」）

上面第 2 节的「静默盈亏平衡点 = 576 秒」和「v3 参数」**已被本节推翻**，以此节为准。

### 发现 1：HTTP 503/403/404/410 ≠ 限速，静默是纯浪费（有直接证据）
当天日志：
```
10:14:30 HTTP503 1357007773.zip off=17104896   ← 17.31MB 的包已下到 98.8%
10:14:30 REST ... 静默等待额度回血（min=300s max=900s）
10:30:03 REST-TIMEOUT 静默 900s 仍未恢复，跳过本轮
10:30:03 RETRY 1357007773.zip attempt=1/3 err=no-recovery
10:31:17 OK   1357007773.zip 17.31MB 1533s(活跃 66s)   ← 重试只用 11 秒！
```
**900 秒静默换来一个 11 秒就能完成的重试。** 当天约 40% 时间耗在这上面。
已改：`503/403/404/410` 一律**立刻重握手**，不进静默；并加 `--max-relinks 8`
（**下了 4MB 以上就清零计数** —— 否则大书合法换链 9 次会被误杀）。

### 发现 2：额度回血速率 ≈10KB/s < 地板 16KB/s ⇒ 任何静默都亏
实测「静默 ↔ 爆发」：120s→1~2MB、900s→9MB、3.6 天→8.8MB（有天花板）。
回血只有 ≈10KB/s，**低于地板的 16KB/s** → 等不如拉。之前算的「576s 打平」用了
「静默多久都能拿满 9MB」的错误假设（实测 120s 只回 1~2MB），故 576 这个数不成立。
→ `--rest-min 0 --rest-max 0`，完全不静默。

### 发现 3：改动效果（已验证）
- 卡住的那本 `1357007449.zip`（旧逻辑 503→静默）**26 秒**下完：`OK 1357007449.zip 3.47MB 26s`。
- 新常驻进程：`10:39:26 START v3 packs=11348 already_ok=63` → `PROGRESS win=15KB/s throttles=0 rests=0`
  持续稳态；PID 7052，父进程 26512(explorer) 已退出 → **脱离成功**。

### 当前参数（v4，写在 `tools/run_downloader.vbs` 里）

```
--workers 1 --limit 0 --loop
--rest-min 0 --rest-max 0 --max-relinks 8 --relink-backoff 5
--slow-window 10 --slow-bytes 65536      # 6.5KB/s 才算真卡住（必须低于地板 16KB/s）

```
工期诚实口径：**16KB/s → 全量约 173 天（约半年）**，静默救不了它，这是免费档硬上限。
