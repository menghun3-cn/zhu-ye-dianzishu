## 二、限速真相（实测重测，**推翻了之前的判断**）

用两个专门的探针（`tools/_diag_parallel.py`、`tools/_diag_sustain.py`）实测：

```
fast  165-usw-data.tv002.com   前 9.1 秒拉了 9.04 MB（971 KB/s）→ 之后一路恒定 16 KB/s
slow   94-cucc-data.tv002.com  前 85 秒 34 KB/s                → 之后也是恒定 16 KB/s
```

**三条结论：**

1. **爆发额度只有约 9 MB（不是之前以为的 30~100 MB）**，速率约 1 MB/s。
   旁证：本次会话启动后 139 秒内下了 2.82 + 1.72 + 4.24 = **8.78 MB** 就掉速；
   而**静默 3.6 天之后重启，爆发也只有 8.8 MB** —— 额度有上限，静默再久也不会变大。
2. **地板 16 KB/s 是「可以一直用的速率」，不是「被封了」。**
   这是最重要的认知修正：额度耗尽后**继续下载就能稳定拿到 16 KB/s**，
   根本不需要静默几十分钟去等它回血（探针连续 600 秒、每 8 秒稳定 128 KB，一刻没停）。
3. **额度按账号/IP 共享，不按 CDN 主机。**
   两条完全不同的线路在同一时刻**一起**掉到 16 KB/s。
   之前看到 `*-usw-data` 跑 500 KB/s 就以为它是「好主机」是**错的** ——
   那只是当时额度刚好是满的，与主机无关。
   → 所以「换主机」「多线程并行」都拿不到额外额度。这一点已被实测证伪，不必再试。

### 额度回血速率（≈10 KB/s）**低于**地板下载速率（16 KB/s）⇒ 任何静默都是净亏

实测「静默多久 ↔ 能爆发多少」：

| 静默时长 | 恢复后的爆发量 |
| --- | --- |
| 120 s | ≈ 1~2 MB（即回血 ≈10 KB/s） |
| 900 s | ≈ 9 MB（线性段上限） |
| 3.6 天 | ≈ 8.8 MB（**有天花板，等再久也不会更大**） |

把爆发换算成「省下的时间」：静默 R 秒换来 ≈ R×10KB/s 的爆发，这些字节用地板拉本来要
R×10/16 ≈ 0.625R 秒 —— **省 0.625R，却花掉 R，净亏 0.375R**。饱和段（只能拿 9 MB）更亏。

**所以不是「静默超过 576 秒才亏」，而是任何长度的静默都亏**（576 那个数用了
「静默多久都能拿满 9 MB」的错误假设，实测 120 s 只回 1~2 MB，该假设不成立）。
→ 结论：**完全不静默**。

## 三、已做的调整（当前生效）

### 1. 参数（v4）

| 参数 | 旧 | 新 | 原因 |
| --- | --- | --- | --- |
| `--slow-bytes` | 262144（=32 KB/s 判限速） | **65536**（10 秒窗口 = 6.5 KB/s） | 旧阈值**高于地板 16 KB/s**，会把正常下载误判成限速 → 触发无谓静默 |
| `--rest-min / --rest-max` | 900 / 5400 | **0 / 0（不静默）** | 额度回血只有 ≈10 KB/s < 地板 16 KB/s，静默是纯亏 |
| `--max-relinks / --relink-backoff` | 无 | **8 / 5 秒** | 防止"死文件"无限空转；**下了 4 MB 以上就清零计数**，避免大书合法换链被误杀 |
| `--pack-timeout` | 1800 | **10800** | 地板速率下 100 MB 的书要约 6400 活跃秒，旧值让**所有大书必然失败** |
| `--max-rest-cycles / --max-attempts` | 4 / 2 | **12 / 3** | 给大书足够耐心 |

### 1b. 【关键修正】HTTP 503 / 403 / 404 / 410 **不是限速**，是链接失效

之前把 503 和慢块一样当成「额度耗尽」→ 去静默 300~900 秒，**这是最大的一笔浪费**。当天日志：

```
10:14:30 HTTP503 1357007773.zip off=17104896     ← 17.31 MB 的包已下到 98.8%
10:14:30 REST ... 静默等待额度回血（min=300s max=900s）
10:30:03 REST-TIMEOUT 静默 900s 仍未恢复，跳过本轮
10:31:17 OK   1357007773.zip 17.31MB 1533s(活跃 66s)   ← 重试只用 11 秒就下完了
```

**900 秒的静默，换来一个 11 秒就能完成的重试。** 当天约 40% 的时间耗在这上面。
原因是 `downurl` **有时效** —— 地板速率下一本大书要拉 1~2 小时，链接必然中途过期。

改掉之后：同一本 `1357007449.zip`（旧逻辑卡在 3.2 MB 触发 503→静默）**26 秒**下完。

生效后的稳态：`win=15~16KB/s  throttles=0  rests=0` —— 不误判、不空等、踩着地板持续拉。

### 2. 三层常驻机制（解决「一断就停 3 天」）

| 层 | 手段 | 覆盖的故障 |
| --- | --- | --- |
| 1 | `tools/run_downloader.vbs`：**幂等**（已在跑就退出）+ 隐藏窗口 | 防多实例抢同一个 `.part` |
| 2 | 用 `explorer.exe` 当父进程启动它 → **脱离工具进程树** | **会话结束不再被回收** |
| 3 | 同一脚本放进开机启动项 + 每 2 小时的**看门狗自动化** | 重启 / 进程崩溃 |

`schtasks.exe` 被安全策略拉黑，上述方案**完全不依赖它**。
验证方式：查进程的 `ParentProcessId`，**父进程已退出**即说明脱离成功（本次实测已脱离）。

### 3. 绝不能删的两个东西

- `data/download-state.jsonl` —— 已完成/失败记录，删了会重下已有的。
- `E:\chinabook\.tmp\*.part` —— **断点续传的本体**，删了所有半成品作废。
